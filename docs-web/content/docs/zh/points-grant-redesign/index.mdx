Herald 积分系统把 `subscription_credit`（订阅积分）和 `free_periodic_credit`（免费周期积分）从"周期预发整期额度"改为**按需计算的滚动窗口配额**。`topup_credit` / `registration_credit` / `granted_credit` 仍保持池子模型不变。

## 给谁看

- 需要配置订阅/免费周期配额的产品或运营人员
- 需要理解消费协调与余额展示逻辑的前端/后端开发者
- 需要接入 SDK 消耗积分或查询余额的第三方开发者

## 前置知识

- 了解 Herald 的 Realm、积分账户、Entitlement Mapping 基本概念
- 熟悉 JSON 和 REST API 调用

## 解决了什么问题

### 周期中途加入的用户也能立即获得额度

旧模型在周期开始时后台预发整期额度。如果用户在 6 月 20 日才订阅一个 6 月 1 日开始的月付套餐，必须等待后台补发或下一周期。新模型按消费/查询时刻实时计算可用窗口额度，首访即得（`backend/domain/src/points/service.rs` 的 `reconcile_due_for_user` 已改为纯读路径确认，不再预发）。

### 不活跃用户零后台开销

取消全表预发后，不活跃用户不会被后台调度扫描、写入或回收。`points_quota_entitlements` 权益记录只在订阅 paid/续费、注册或升级时创建，用量来自 `points_transactions(type='consume')` 聚合，不需要独立的 usage_log。

### 多时间窗叠加的严格上限

一个权益可以配置多个窗口，例如 `{5h: 500, week: 5000, month: 20000}`。任意时刻的可用额度 = 各窗口"上限 − 窗口内已用量"的最小值。如果 5 小时窗已用满，即使周窗/月窗还有剩余，当前可用额度也是 0。

### 单次消费自动协调窗口额度与池子余额

消费时在同一事务内先扣窗口额度，超额部分原子转充值/注册/发放池；合计不足整体回滚拒绝，不会部分扣减。

## 关键模型对比

| 积分类型 | 计费模型 | 说明 |
|---|---|---|
| `subscription_credit` | 滚动窗口配额 | 按消费时刻实时计算，不预写整期额度 |
| `free_periodic_credit` | 滚动窗口配额 | 按消费时刻实时计算，不累积 |
| `topup_credit` | 池子模型 | 用户主动购买，长期有效（除非配置有效期） |
| `registration_credit` | 池子模型（永久有效） | 注册时一次性赠送，升级到付费后保留 |
| `granted_credit` | 池子模型 | 管理员或 SDK 主动发放，可配置有效期 |
