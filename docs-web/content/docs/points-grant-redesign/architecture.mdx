points-grant-redesign moves subscription/free-periodic credits from "pre-granted ledger rows" to "quota entitlements + rolling-window usage". Topup/registration/granted credits still go through the original pool path.

## Backend components

### Quota Entitlement

`backend/domain/src/points/entities.rs` defines the core entity:

```rust
pub struct QuotaWindow {
    pub window_seconds: i64,
    pub limit: i64,
    pub key: String,
}

pub struct PointsQuotaEntitlement {
    pub id: Uuid,
    pub user_id: Uuid,
    pub realm_id: String,
    pub bucket_id: Uuid,
    pub credit_type: CreditType,        // subscription_credit / free_periodic_credit
    pub source_type: QuotaSourceType,   // subscription_initial / subscription_renewal / subscription_upgrade / free_periodic_grant
    pub source_id: String,
    pub quota_windows: Vec<QuotaWindow>, // snapshot
    pub effective_from: DateTime<Utc>,
    pub effective_until: Option<DateTime<Utc>>,
    pub status: QuotaEntitlementStatus, // active / revoked / expired
    pub idempotency_key: String,
}
```

The storage table is `points_quota_entitlements` (see `.ai/design/points-grant-redesign.md` §4.3.2). The unique constraint is `(realm_id, user_id, bucket_id, credit_type, idempotency_key)`, guaranteeing that the same subscription period or registration source is never granted twice.

### Lifecycle management

`backend/domain/src/points/subscription_service.rs` handles granting and revocation:

- `grant_quota_entitlement`: called on subscription paid/renewal, upgrade, or free registration
- `revoke_quota_entitlement`: called on subscription cancel/refund, or on free-to-paid upgrade

Revocation only sets `status = revoked` and `effective_until`; it does not reverse-adjust already-consumed transactions. Used quota is released naturally as the window rolls.

### Window aggregation

`backend/domain/src/points/service.rs` provides:

- `compute_window_available_for_credit_type`: computes the window-available quota for a `(user, bucket, credit_type)`
- `compute_quota_windows_view`: returns the window view used by the frontend dashboard

Window usage comes from the covering index `idx_points_transactions_window_agg` on `points_transactions`:

```sql
CREATE INDEX idx_points_transactions_window_agg
  ON points_transactions (user_id, bucket_id, credit_type, created_at DESC)
  INCLUDE (amount)
  WHERE type = 'consume';
```

Aggregation rules (`aggregate_quota_windows`):

1. Group by `key`, aggregating all active entitlements under the same `(user, bucket)`
2. For windows sharing the same `key`: sum the limits, take the max of used (windows of the same length share the same sliding interval)
3. `remaining = max(0, limit - used)`
4. Final available quota = the minimum of `remaining` across all `key`s

### Mixed consumption

`backend/infra/src/points/postgres_repository.rs` performs the following inside the `consume_points_atomic` transaction:

```text
BEGIN
Lock points_wallets row (FOR UPDATE)
window_avail = window-available quota for this account
pool_avail   = pool-type available quota (topup/registration/granted)
if amount > window_avail + pool_avail: ROLLBACK, return InsufficientBalance
window_part = min(amount, window_avail)
pool_part   = amount - window_part
if window_part > 0: write points_transactions(type='consume', credit_type=subscription/free_periodic)
if pool_part > 0:  debit points_credit_ledger in ascending expires_at order, and write the matching consume rows
Update wallet stats
COMMIT
```

This guarantees a single consume either fully succeeds or does not debit at all.

### Correctness boundary of lazy granting

`backend/domain/src/points/service.rs`'s `reconcile_due_for_user` is now a pure read path — it only confirms whether an active quota entitlement currently covers the present moment, and performs no writes. Therefore:

- Background jobs not running does not affect balance or consume correctness
- A user subscribing mid-period gets the window quota on first access / first consume
- Inactive users incur no background pre-grant or reclaim overhead

## Frontend components

### User balance page

Route: `/{realmId}/user/points`; component `frontend/src/components/points/UserPointsPage.tsx`.

Page structure:

1. Cross-account total area (shown when the user holds 2 or more accounts)
2. A `PointsUsageDashboard` per account (window model)
3. A `PointsBalanceCard` per account (pool model)
4. Transaction history

`PointsUsageDashboard` shows:

- The total currently consumable amount `bucketTotal`
- A formula hint: "minimum of remaining across windows + top-up balance"
- One row per window: key, limit, used, remaining, progress bar, recovery time, tightest-constraint / exhausted marker

`PointsBalanceCard` shows pool-type balances only (topup/registration/granted); subscription/free-periodic balances are owned by the dashboard.

### View derivation

`frontend/src/components/points/user-points-view.ts`'s `deriveUserPointsView` filters the realm-wide data returned by `listWallets` down to the current-user view, producing:

```typescript
interface DerivedBucketCard {
  bucketId: string
  name: string | null
  enabled: boolean | null
  bucketTotal: number
  balancesByType: BalancesByType
  quotaWindows: QuotaWindowViewDto[] | null
  spendableFromQuota: number | null
  spendableFromPool: number | null
}
```

### Multi-window quota editor

`frontend/src/components/billing/MultiWindowQuotaEditor.tsx` is a controlled component used by both:

- `frontend/src/components/billing/entitlement-mappings-page.tsx` (subscription quotas)
- `frontend/src/routes/$realmId/manage/points/default-config.tsx` (free-period quotas)

The editor's input and output are `QuotaWindowInputDto[]`, each row carrying `windowSeconds` and `limit`. The display layer offers unit switching (seconds/minutes/hours/days/weeks/months-30d), but only `windowSeconds` travels over the wire.

### Data queries

`frontend/src/data/query-options.ts` defines:

- `walletsByBucketQueryOptions(realmId)` → `GET /api/points/{realmId}/wallets`
- `pointsDefaultConfigQueryOptions(realmId)` → `GET /api/points/{realmId}/default-config`
- `entitlementMappingsQueryOptions(realmId, filters)` → fetch the Entitlement Mapping list

`listWallets` hard-isolates `points.view`-only users to their own wallet rows; admins can view the whole tenant.
