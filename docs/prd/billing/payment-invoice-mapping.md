## 2. 范围界定

### 2.1 包含功能

- **订阅续费的支付记录**：Stripe / Creem 订阅每次成功续费扣款都产生一条支付尝试记录，与一次性支付、订阅首期采用同一“每次支付”记录模型（US-PM-001）。
- **Creem 订阅续费发票映射**：补齐 Creem 续费的发票同步，使 Creem 订阅每个周期在 Herald 都有一张映射发票，与 Stripe 续费对齐（US-PM-002）。
- **外部发票的本地归属**：所有第三方（Stripe / Creem）同步的发票，都显式归属到本地支付尝试（一次性 / 续费）或订阅，可在数据层直接定位，无需间接推断（US-PM-003）。
- **补偿与可观测性**：发票同步 / 归属回填在依赖未就绪或临时失败时可补偿；“有支付无发票”与“发票无归属”两类异常对管理员可发现、可筛选，失败可观测（US-PM-004）。

### 2.2 不包含功能 (Out of Scope)

- **Manual 自研发票允许无对应支付**：强制映射约束只作用于第三方托管支付的同步路径；自研发票维持现状，允许赠票 / 线下款等无对应支付场景。
- **历史数据不回填**：既有外部发票的空归属不做补录，仅对新发生的同步路径生效。
- **Herald 主动为 Creem 开自研发票 / 退款**：维持 Creem 作为 Merchant of Record 的既有边界（沿用 US-IF-003 / 现有发票资格策略），不改变其对外语义。
- **前端新增独立页面或导航入口**：归属信息只在既有发票列表与发票详情中以只读方式呈现，不新增独立页面、路由或导航入口。

### 2.3 依赖项

- **Stripe / Creem webhook 同步框架**（幂等、重试、补偿机制）—— 本特性复用并扩展。
- **支付尝试既有模型**（一次性支付 + 订阅首期 checkout）—— 本特性扩展到续费场景。
- **外部发票同步模型**（external_sync 来源、外部发票 / 订单标识）—— 本特性复用。
- **现有发票资格策略与 Creem MoR 边界**—— 本特性不改变其对外语义。

## 3. 需求概述

### 3.1 功能描述

当前第三方托管支付（Stripe / Creem）的发票映射存在两处断层：

1. **覆盖断层**：Stripe 订阅每个周期都有发票，但 Creem 订阅只有首期 checkout 同步了发票，续费周期完全没有发票映射。
2. **根因断层**：订阅续费在本地根本没有支付尝试记录——续费只更新订阅周期并发放积分。于是既没有“这次支付”的账本记录，发票也没有可归属的锚点；同时所有外部同步发票的本地归属字段为空，“发票属于哪笔支付”只能靠外部标识间接推断。

本特性把“每一次用户支付（含订阅续费）都应被记录、并映射一张可归属的发票”确立为产品规则：支付尝试成为记录每次支付的统一账本，发票显式归属到它或订阅。

### 3.2 关键特性

- **支付记录的完整性**：一次性支付、订阅首期、订阅续费统一纳入支付尝试记录，每一次成功扣款都留下记录。
- **发票映射的对称性**：Stripe 与 Creem 在订阅续费场景下的发票覆盖一致，消除“有支付无发票”。
- **归属的直接性**：从发票可直接、显式地定位到本地支付或订阅，而非间接推断。
- **可靠性的可发现性**：缺失 / 断链可被补偿和观测，不长期静默存在。

## 4. 业务规则与状态

### 4.1 业务规则

- **每次成功支付一张发票**：每一笔成功的第三方托管支付（含订阅续费）在 Herald 都映射且仅映射到一张发票。
- **每次成功支付一条支付记录**：订阅续费与一次性 / 首期支付一样，产生一条支付尝试记录；扣款失败的周期不产生已成功记录。
- **零元周期不产生支付记录与发票**：100% 折扣或免费档的零金额周期无实际扣款，既不产生续费支付尝试，也不产生续费发票；订阅周期与积分照常更新。
- **发票显式归属**：第三方同步发票必须归属到本地支付尝试（一次性 / 续费）或订阅；续费发票同时归属本次续费的支付尝试与其订阅。
- **Creem MoR 边界不变**：Herald 不主动为 Creem 交易开自研 / 退款发票，仅同步第三方已开发票；Creem 发票为只读。
- **幂等**：重复的 webhook / 补偿事件不产生重复的支付记录或发票。
- **静默禁止**：发票同步或归属回填失败不得被静默吞掉而表现为“正常”；缺失或断链必须可识别。

### 4.2 关键状态与异常

- **续费支付记录的识别**：续费产生的支付尝试须可区别于首期，且可按订阅归集。
- **归属缺失状态**：当外部发票暂时无法归属到本地支付 / 订阅（如本地记录未就绪）时，进入“待归属”而非“已正常”，并在就绪后补偿回填。
- **断链状态**：发票存在但无法定位到支付的“断链”情况，须可被发现并经补偿恢复。
- **权限可见性**：续费发票及其归属信息沿用现有发票的访问控制——管理员可见完整归属与对账维度；普通用户仅见自身发票摘要，发票详情不暴露内部支付尝试标识。

## 5. 功能需求

### 5.1 核心需求

- 订阅续费（Stripe 续费周期、Creem 续费）产生支付尝试记录，记录金额、币种、支付平台、完成时间、归属订阅（US-PM-001）。
- Creem 订阅续费同步发票，每个续费周期一张，状态已支付，含金额 / 币种 / 税务信息 / Creem 外部标识（US-PM-002）。
- 第三方同步发票在同步时回填本地归属：一次性发票 → 支付尝试；订阅发票（含续费）→ 订阅；续费发票 → 同时关联本次续费支付尝试（US-PM-003）。
- 发票同步 / 归属回填失败时通过既有补偿机制重试；“有支付无发票”与“发票无归属”异常可被管理员识别并筛选；失败被记录并可在运维侧查看（US-PM-004）。

### 5.2 验收目标

- 一个通过 Creem 完成多次续费的订阅，其每一个已成功续费周期在 Herald 都有一条支付尝试记录和一张映射发票，与 Stripe 订阅续费的覆盖一致。
- 任意一张第三方同步发票，都能直接定位到其归属的本地支付尝试或订阅；不存在“已正常展示但归属为空”的外部发票。
- 模拟“本地支付记录未就绪”或“关联临时失败”后，补偿机制能恢复发票与归属，不产生永久缺失或断链。
- 管理员能识别并筛选“成功支付但无发票”与“发票无归属”两类异常。

## 6. API 相关约束

**适用性**: 适用（仅约束接口能力边界，不含端点 / 参数明细）

- **能力范围**：发票列表与详情的查询响应须能体现归属信息（归属的支付尝试 / 订阅），用于前端只读展示与管理员对账；管理员可按“无归属”筛选发票，并可查询“无归属发票”与“已成功支付但无发票”两类归属异常。归属完整性由后端在同步与写入路径保证，不新增面向终端用户的写入能力。
- **访问控制**：归属信息遵循现有发票访问控制——管理员可见完整归属与对账维度；普通用户仅见自身发票摘要，发票详情不暴露内部支付尝试标识。
- **租户 / Realm 边界**：所有归属查询与回填均在 realm 隔离内进行，沿用现有 realm 边界。
- **兼容性**：不破坏现有发票同步（US-IF-002 / US-IF-003）与支付履约（US-PA-003）的对外语义；外部发票外部标识策略不变。

---

## 7. 前端/交互约束

**适用性**: 部分适用

- **无新增页面或导航入口**：不新增独立页面、路由或导航；归属信息只在既有发票列表与发票详情中以只读方式呈现。
- **发票详情归属展示**：发票详情以只读方式展示归属信息——归属订阅（可跳转到订阅列表）与归属支付尝试；两个字段均为空时该区块隐藏。
- **发票列表归属维度**：管理端发票列表支持按“全部归属 / 无归属”筛选；对无归属的外部发票行给出可识别的“无归属”标记；Manual 自研发票不参与无归属标记。
- **状态反馈**：续费发票在发票列表 / 详情沿用现有外部发票展示规则（只读、来源标识、Creem 不展示退款维度等）。
- **权限可见性**：普通用户不暴露内部支付尝试标识；管理员可见归属与异常维度用于对账。

## 8. 已确认决策

- **强制映射范围限定为第三方托管支付**：强制映射约束只作用于第三方托管支付（Stripe / Creem）的同步路径（含订阅续费），不扩展到 Manual 自研发票（已确认）。
- **订阅续费由支付尝试账本承载**：每次续费产生一条已成功的支付尝试记录作为“本次支付”账本，并作为续费发票的归属锚点（已确认方向）。
- **维持 Creem 作为 Merchant of Record 的既有边界**：Herald 只同步 Creem 已开发票，不主动开自研 / 退款发票。
- **复用既有 webhook 幂等、重试与补偿机制**，不另起基础设施。
- **Manual 自研发票允许无对应支付**：自研发票不要求归属到支付，赠票 / 线下款等无支付场景允许（已确认）。
- **归属完整性在同步时建立**：新同步的外部发票在同步写入时即建立本地归属；既有的历史空归属不做回填（已确认）。
- **不回填历史数据**：既有外部发票的空归属不补录，仅对新同步路径生效（已确认）。
