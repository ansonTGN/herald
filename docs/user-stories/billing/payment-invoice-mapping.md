## 用户故事

### 故事 1：订阅续费记录每一次支付 [US-PM-001]

**优先级**: P0

**【用户故事】**
**作为**：Herald 系统（详见 [docs/user-stories/_roles.md](/docs/user-stories/_roles.md)）
**我希望**：为订阅的每一次续费支付都记录一条支付尝试
**从而**：有一处统一的地方记录用户的每一次支付（含订阅续费），用于对账、退款追溯，并作为发票的归属锚点

**【验收标准】**

> 验收标准只描述用户动作与可见结果，不写 API 路径、数据表、字段变更、技术实现步骤。

**场景 1：Stripe 订阅续费记录支付**
```gherkin
Given 一个处于活跃状态的 Stripe 订阅进入下一计费周期
And 该周期扣款成功
When 系统收到该周期的支付成功通知
Then 系统记录一条本次续费的支付尝试
And 该支付尝试包含金额、币种、支付平台（Stripe）、完成时间
And 该支付尝试归属于对应的订阅
And 支付尝试状态为已成功
```

**场景 2：Creem 订阅续费记录支付**
```gherkin
Given 一个处于活跃状态的 Creem 订阅进入下一计费周期
And 该周期扣款成功
When 系统收到该周期的续费通知
Then 系统记录一条本次续费的支付尝试
And 该支付尝试包含金额、币种、支付平台（Creem）、完成时间
And 该支付尝试归属于对应的订阅
And 支付尝试状态为已成功
```

**场景 3：续费支付尝试可区别于首期**
```gherkin
Given 一个订阅已完成首期支付并产生过若干次续费
When 系统列出该订阅的支付尝试
Then 每条续费支付尝试都能被识别为该订阅的续费记录
And 首期支付尝试与各续费支付尝试互不混淆
```

**场景 4：扣款失败的周期不记录为已成功**
```gherkin
Given 某订阅在一个计费周期扣款失败
When 系统收到该周期的失败通知
Then 系统不为该周期创建状态为已成功的支付尝试
```

### 故事 2：Creem 订阅续费同步发票 [US-PM-002]

**优先级**: P0

**【用户故事】**
**作为**：Herald 系统
**我希望**：为 Creem 订阅的每一次续费支付同步一张发票
**从而**：每个续费周期在 Herald 都有对应的发票映射，与 Stripe 续费保持一致，不出现"有支付却无发票"

**【验收标准】**

**场景 1：Creem 续费产生发票映射**
```gherkin
Given 一个 Creem 订阅完成一次续费支付
When 系统处理该续费通知
Then Herald 创建（或更新）一条来源为 Creem 的发票记录
And 发票状态为已支付
And 发票记录本次续费的金额、币种与税务信息
And 发票记录 Creem 的外部标识
```

**场景 2：Creem 续费发票为只读**
```gherkin
Given Herald 存在一条来源为 Creem 的续费发票
When 任何用户尝试通过 Herald 编辑、开具、作废或标记该发票已付
Then 系统拒绝操作
And 提示该发票由 Creem 管理
```

**场景 3：重复续费通知幂等**
```gherkin
Given Herald 已为某次 Creem 续费同步过发票
When Herald 再次收到同一次续费的通知
Then Herald 更新已有记录而非创建重复发票
```

**场景 4：Creem 续费与 Stripe 续费发票覆盖一致**
```gherkin
Given 同样是订阅续费场景
When 分别通过 Stripe 与 Creem 完成一次续费
Then 两种平台在该续费周期都各自有一张映射发票
And 不存在"Stripe 续费有发票、Creem 续费无发票"的不一致
```

### 故事 3：外部发票归属本地支付或订阅 [US-PM-003]

**优先级**: P1

**【用户故事】**
**作为**：Herald 系统
**我希望**：每一张第三方同步的发票都能直接定位到它归属的本地支付尝试或订阅
**从而**："这张发票对应哪笔支付、哪个订阅"在数据层可直接回答，无需间接推断

**【验收标准】**

**场景 1：一次性支付发票归属支付尝试**
```gherkin
Given 一张来自 Stripe 一次性购买的同步发票
Then 该发票归属到对应的本地支付尝试
And 可从发票直接定位到这笔一次性支付
```

**场景 2：订阅发票归属订阅**
```gherkin
Given 一张订阅（首期或续费）的同步发票
Then 该发票归属到对应的本地订阅
And 可从发票直接定位到该订阅
```

**场景 3：续费发票同时归属支付尝试与订阅**
```gherkin
Given 一张订阅续费的同步发票
Then 该发票既归属本次续费的支付尝试
And 也归属该订阅
```

**场景 4：归属缺失可被发现而非静默**
```gherkin
Given 某张外部同步发票无法归属到任何本地支付或订阅
When 系统完成同步
Then 该归属缺失情况被识别并暴露
And 而不是静默保留为可正常展示、却无归属的发票
```

### 故事 4：发票-支付映射的补偿与可观测性 [US-PM-004]

**优先级**: P2

**【用户故事】**
**作为**：Herald 系统 / Realm Admin
**我希望**：在发票同步或归属回填失败时能自动补偿并被观测
**从而**：避免"支付成功但发票缺失或断链"长期存在而不被发现

**【验收标准】**

**场景 1：本地支付尝试未就绪时延迟补偿**
```gherkin
Given 一笔第三方支付的通知先于本地支付尝试记录到达
When 系统暂时无法为该支付写入发票
Then 系统在本地支付尝试就绪后补偿写入对应的发票
And 不永久丢失该发票
```

**场景 2：Stripe 一次性支付关联失败可补偿**
```gherkin
Given 一笔 Stripe 一次性支付的发票与支付的关联未能成功建立
When 系统执行补偿重试
Then 系统恢复该发票与其对应支付之间的关联
And 不出现"发票存在但永久无法定位到支付"的断链
```

**场景 3：缺失或断链可被管理员发现**
```gherkin
Given 存在"成功支付但无发票"或"发票无归属"的异常情况
When 管理员查看发票或对账相关视图
Then 管理员能够识别这些异常情况
And 而不是完全无法察觉
```

**场景 4：失败可观测**
```gherkin
Given 发票同步或归属回填发生失败
Then 该失败被记录
And 可在运维侧查看
```
